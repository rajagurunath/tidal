\caption[The batching lineage]{\textbf{How serving learned to batch, and where Tidal
sits.} Rows are engine slots, columns are iterations, cells are scheduled tokens.
\emph{(a) Static batching} runs a fixed group to completion, so every early finisher
idles until the longest request ends. \emph{(b) Dynamic batching} re-forms groups
between runs; arrivals queue less, but the waste inside each run remains. \emph{(c)
Continuous batching}~\citep{orca} rebuilds the working set every iteration and chunked
prefill~\citep{sarathi} slices prompt processing under the token budget $\tau$ ---
which removes the batching waste, but cannot conjure work: sparse online traffic
leaves $\tau$ unspent. \emph{(d) Tidal} fills that remainder with tokens from
deadline-contracted batch jobs, capped by the latency model and KV guardband so online
work always has the room it needs. Each step widens what may share one iteration:
requests of different lengths, then requests at different phases, then --- here ---
two different products.}
\label{fig:batching}
